# دليل تشغيل البيانات والاستعادة

هذا الدليل لمن يدير المنظومة. يشرح أين تُحفظ البيانات، وكيف تُحمى، وكيف تُسترجع عند الطوارئ.

## 1. أين تُحفظ البيانات

| المكان | ما فيه |
|---|---|
| **D1** (`etihad-company-data`) | الحسابات والصلاحيات، وبيانات الأقسام، والمحادثة، وسجل العمليات، وسجل النسخ والمهام |
| **R2** (`etihad-files`) | محتوى الملفات: `sahara/` و `chat/`، وسلة المحذوفات `trash/` |
| **R2** (`etihad-backups`) | النسخ الاحتياطية: `daily/` و `manual/` و `pre-restore/` و `monthly/` و `migrations/` |

- **الواردات والإشعارات والدفاتر المالية والمهام** محفوظة في جدول `collection_items`، وكل سجل في سطر مستقل.
- **للاستعلام والتقارير** نستخدم العروض: `v_sahara_inbound_deliveries` و `v_etihad_inbound_deliveries` و `v_notifications`.

## 2. الحماية التلقائية

- **نسخة يومية** الساعة 03:00 بتوقيت العراق، وتُحفظ في `daily/YYYY/MM/`.
- **صيانة شهرية** في أول كل شهر، وفيها:
  - دمج نسخ الشهر السابق في `monthly/YYYY-MM.ndjson.gz`. هذا الأرشيف **يبقى دائمًا**.
  - أرشفة الإشعارات الأقدم من 90 يومًا، وسجل العمليات الأقدم من 180 يومًا.
  - تنظيف البيانات المؤقتة.
  - **فحص سلامة الملفات** بمقارنة بصمات SHA-256.
  - تفريغ ما مضى عليه أكثر من 30 يومًا في سلة المحذوفات.
- **بصمة SHA-256** لكل نسخة احتياطية ولكل ملف، ويُتحقق منها قبل أي استرجاع.
- **الملفات المحذوفة** تبقى في سلة المحذوفات 30 يومًا، ويمكن استرجاعها من لوحة إدارة النظام.
- **حد لمحاولات الدخول:** بعد 20 محاولة فاشلة من نفس الجهاز خلال 15 دقيقة يُرفض الدخول. وهذا إضافة إلى قفل الحساب نفسه بعد 5 محاولات.

كل هذا يُدار ويُراقب من: **الإعدادات ← إدارة النظام**.

## 3. إعدادات يُنصح بتفعيلها في حساب Cloudflare (مرة واحدة)

### قفل الأرشيف الشهري ضد الحذف أو الكتابة فوقه
```bash
npx wrangler r2 bucket lock add etihad-backups monthly-archive-lock "monthly/" --retention-indefinite
```
```bash
npx wrangler r2 bucket lock list etihad-backups
```
- **لا تقفل `daily/`.** الصيانة الشهرية تحذف النسخ اليومية بعد دمجها في الأرشيف.
- القفل لا يمنع كتابة أرشيفات جديدة. المهمة الشهرية لا تكتب فوق أرشيف موجود، بل تضيف لاحقة رقمية للاسم.

### D1 Time Travel (موجود تلقائيًا)
يمكن إرجاع قاعدة البيانات كاملة إلى أي دقيقة خلال **30 يومًا** في الباقة المدفوعة، أو **7 أيام** في المجانية.

```bash
npx wrangler d1 time-travel info etihad-company-data
```
```bash
npx wrangler d1 time-travel info etihad-company-data --timestamp="2026-10-05T03:00:00+03:00"
```
```bash
npx wrangler d1 time-travel restore etihad-company-data --bookmark=BOOKMARK_ID
```
- **هذه العملية تكتب فوق القاعدة كلها، وتلغي الاستعلامات الجارية.**
- أمر الاسترجاع يعيد رمزًا (bookmark) للحالة السابقة، فيمكن التراجع عنه.

### تصدير نسخة SQL كاملة إلى جهازك
```bash
npx wrangler d1 export etihad-company-data --remote --output=./etihad-backup.sql
```
القاعدة تتوقف عن خدمة الطلبات الأخرى أثناء التصدير، فنفّذه خارج أوقات العمل.

## 4. الاسترجاع في الطوارئ (اختر حسب الحالة)

| الحالة | الحل |
|---|---|
| **حذف ملف بالخطأ** | إدارة النظام ← الملفات ← سلة المحذوفات ← استرجاع |
| **خطأ في البيانات اليوم أو أمس** | إدارة النظام ← النسخ ← اختيار نسخة ← استرجاع. تؤخذ نسخة "قبل الاسترجاع" تلقائيًا للتراجع |
| **تلف واسع أو خطأ قبل دقائق محددة** | `wrangler d1 time-travel restore` إلى ما قبل الخطأ مباشرة |
| **البرنامج نفسه لا يعمل** | من لوحة Cloudflare ← R2 ← `etihad-backups`، نزّل آخر نسخة `.json.gz` |

### إذا كان البرنامج لا يعمل
- الملف المنزّل هو JSON مضغوط، وفيه كل الجداول وعدد سطور كل جدول.
- يمكن رفعه من جديد عبر لوحة إدارة النظام بعد إصلاح البرنامج، أو استخدام Time Travel مباشرة.

### قبل أي نشر كبير
خذ "نسخة احتياطية الآن" من لوحة النظام، وسجّل رمز Time Travel الحالي:
```bash
npx wrangler d1 time-travel info etihad-company-data
```

## 5. بيئة التجربة (staging)

- لها Worker وقاعدة D1 وحاويات R2 منفصلة تمامًا عن التشغيل الفعلي: `etihad-company-data-staging` و `etihad-files-staging` و `etihad-backups-staging`.
- ليس فيها مهام مجدولة.

```bash
npm run deploy:staging
```
```bash
npm run deploy
```
الأمر الأول ينشر بيئة التجربة، والثاني ينشر التشغيل الفعلي. يُختار نوع البيئة وقت البناء عن طريق `.env.staging`، لا عن طريق `--env` في أمر النشر.

## 6. الانتقال إلى PostgreSQL لاحقًا

البنية الحالية جاهزة للانتقال تدريجيًا:

1. **الملفات تبقى في R2** ولا تنتقل. ينتقل فقط جدولا البيانات الوصفية `sahara_files` و `chat_files` مع عمود `sha256`.
2. **العروض `v_*` تقابل جداول PostgreSQL المستقبلية** بأعمدة وأنواع واضحة. أنشئ الجداول في PostgreSQL بنفس الأعمدة، مع `PRIMARY KEY (id)` وقيود `NOT NULL` و `CHECK`.
3. **لنقل البيانات:** صدّر D1 إلى SQL، أو نزّل نسخة JSON من لوحة النظام، ثم انقلها. استخدم `pgloader`، أو سكربت ينقل من العروض إلى الجداول الجديدة.
4. **يبقى Cloudflare Workers هو الخادم.** يُربط بـ PostgreSQL عبر **Hyperdrive**، وتُستبدل استعلامات D1 بمكتبة `postgres`.
5. **أوقف الكتابة أثناء النقل** من إدارة النظام ← الصيانة ← وضع الصيانة. ثم بدّل الاتصال، ثم ألغِ وضع الصيانة.

> **ملاحظة:** SQLite متساهلة في الأنواع، و PostgreSQL صارمة. افحص التواريخ والأرقام الفارغة قبل الاستيراد. العروض تحوّل الأرقام بـ `CAST` مسبقًا، وهذا يسهّل الفحص.
